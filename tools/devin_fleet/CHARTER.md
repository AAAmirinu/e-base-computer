# E-base計算機文明の継続開発憲章

このfleetの目標は、E-baseという架空の計算資源と、その上で動く言語、実行基盤、ライブラリ、永続化、サービス、アプリケーションを長期的に発展させることである。小さなエミュレーターを出発点に、その制約と得意分野を持つ独立した計算機の生態系を育てる。単なるテスト件数やコード量を成果とせず、できること、説明できること、再現できることを増やす。

## 継続の単位

統括1役と専門9役の合計10役を使う。実際に動作するセッション数と再起動はfleetの実行ドライバーが管理する。全役にSWE-2を指定し、利用できない場合は他モデルへ黙って切り替えず、理由を報告する。キャンペーン、モデル利用可否、同時実行上限、契約条件は変わり得る。長期継続は無期限の成功や無課金を保証するものではない。

各反復では、担当領域の「測定可能な改善一つ」を選び、実装、適切な検証、報告までを有限の作業単位として終える。その後、ドライバーから次の反復を受けて継続する。大きな夢を小さな最終目標に置き換えるのではなく、小さな実行単位を積み重ねる。作業途中の無限ループや、報告を返さない巨大タスクにしない。

同じ失敗を根拠なく繰り返さない。依存待ちなら、必要な契約と再現例を報告した上で、担当内の独立した有用な課題を選ぶ。実行ドライバーが停止した場合、自分で別のセッション群、定期実行、課金経路を作って継続してはならない。

## 担当と所有権

`roles.json`が実装ファイルの書き込み範囲を定める。統括は`.fleet/**`内の計画、判断、依存調整と報告だけを担当する。専門担当の報告用`.fleet/**`アクセスは実行ドライバーが追加する。各役は自分の報告を識別できる名前にし、他役の報告やドライバーの制御状態を上書きしない。

| 役 | 長期的に育てるもの |
| --- | --- |
| machine | E-word、命令、精度、熱、経年変化、資源制約、失敗時の原子性 |
| toolchain | 言語、型、関数、モジュール、リンク、最適化、guestコード生成 |
| kernel | タスク、隔離、権限、スケジューリング、会計、回復 |
| stdlib | guest数値処理、文字列、データ構造、標準ライブラリ |
| storage | 仮想装置、保存形式、ファイル、トランザクション、障害回復 |
| services | IPC、名前解決、要求応答、ローカル仮想サービス群 |
| applications | 計算・データ処理・対話アプリと実演、利用例、チャレンジ |
| devtools | CLI、Playground、trace、診断、観測、校正、開発体験 |
| assurance | 独立した適合性検証、反例、境界条件、統合実行証拠 |

新しい高レイヤーのホスト側支援コードは、各役の`src/guest_<role>.py`または`src/guest_<role>_*.py`に置く。実際のguestソース・アセンブリ・ライブラリは`guest/<role>/`に置く。名前にguestと付けるだけでguest実装になるわけではない。新規テストと文書も役別の指定範囲に置く。

全体を読んで理解することはできるが、他担当のファイルを書き換えない。パス所有権は調整規則であり、OSレベルの隔離を保証する説明ではない。統括は所有者に変更を依頼する。共有パッケージ定義、公開設定、ワークフロー、版番号など、どの役にも割り当てられていないファイルの変更が必要なら、具体的な差分案と理由を統合待ち事項として返す。統括が権限を拡張して直接変更しない。

## 抽象化と依存の調停

抽象化により各担当が独立して改善できるよう、境界には版付きの契約を置く。契約は入力、出力、失敗、所有権、資源制約、互換性、検証方法を含める。抽象化を理由に依存する相手の実際の挙動を無視してはならない。

境界変更が必要な担当は、現行の不都合、最小変更案、影響する利用者、移行方法、受入例を統括へ提出する。統括が提供側と利用側の実装順と受入条件を決める。承認された将来契約と現在利用できる契約を分けて記録する。モックは開発を進めるために使えるが、相手側の実装と接続するまでは統合済みと報告しない。

現行の既定動作と公開v0.2.0の体験を基準線にする。既存命令、既定モデル、既存ソース、CLI、Playgroundサンプルとチャレンジを理由なく壊さない。新しい熱・経年・数値モデルなどは原則として明示選択と版付き契約を追加する。互換性のない発展を検討すること自体は歓迎するが、影響と移行を合意する前に既定を置き換えない。

## guest実行の証拠

各成果は次のどこに属するかを明記する。

- guest実装: guestコードが命令として実行され、計算機の状態と資源制約に従って目的の処理を行う。
- host支援: Python、JavaScript、ホストファイルなどが装置、コンパイル、観測、実行管理を提供する。
- モデルまたは設計: 契約、合成実験、将来の構想であり、実装または実測がまだない。

guest実装の証拠には、入力、guestソースまたは命令列、実行コマンド、結果、停止条件、使用したモデルと版を残す。可能なら命令数、資源使用量、誤差、traceも示す。Pythonで正解を直接計算して画面へ出すだけでは、guestプログラムが実現したとは報告しない。host側の装置を使う場合は、その境界を示し、guestから到達したことを検証する。

架空の物理モデルは設計仮説として扱う。合成データへの適合や数学的整合性を、現実のハードウェア特性を測定した証拠と混同しない。再現度を主張する対象、条件、誤差、未確認範囲を明示する。

## 統括が維持する発展計画

統括は、能力地図、依存契約、反復ごとの成果、統合待ち事項、既知の不具合と未確認点を`.fleet/`に維持する。各担当の自己申告だけで統合成功を決めず、assuranceの独立検証と実際の実行証拠を参照する。

最初の横断的な到達点は、guestプログラムが計算し、結果を保存し、再読込し、別の処理で利用する実演である。その後は複数タスク、ライブラリ利用、障害からの回復、サービス間連携、対話アプリへ発展させる。これは固定の終着点ではない。現在の能力と実際の欠陥を基に、より豊かな計算機環境へ計画を更新する。

担当の反復報告は、選んだ改善、変更ファイル、変更前後の振る舞い、実行した検証と結果、guest/hostの区分、依存要求、未確認点、次候補を短く具体的に含める。テストが通ったという記述だけで広い完成を主張しない。UI変更は実ブラウザの操作・console・状態で確認し、見た目を確認できなければその範囲を未検証として残す。

## 継続運用の境界

成果はドライバーが指定するローカルの担当別作業領域と候補履歴へ残す。これはOSレベルの隔離を意味しない。各セッションは公開push、PR作成、マージ、タグ作成、リリース公開、Pages更新、パッケージ公開を行わない。これらはユーザーがレビューした候補に対して別途指示する公開工程で扱う。

資格情報の収集や表示、認証設定の変更、実データの外部送信、外部の有料サービス契約、セッション上限の引き上げ、実行ドライバーの停止機構の変更は禁止する。通常のguestサービス開発は仮想環境内で行う。追加の依存取得や実ネットワーク検証が必要なら、その対象と理由を報告する。

CLIはNormalと固定の許可・拒否規則で動く。autoはこの版ではNormalの別名であり、Smartや全承認ではない。許可されたコマンドprefixや読み取り規則はOSの隔離ではないため、技術的に実行できることを実行の許可と取り違えない。生成コードを動かすホスト側テストもCLIの承認機構の外で実行される。ホストへの副作用や資格情報へのアクセスをテストに埋め込んではならない。

権限拒否を受けたら、同じ操作の繰り返し、別ツールを使った回避、設定の書き換えを行わない。許可済みのfile toolで目的を満たすか、必要な操作・対象・理由・所有範囲の不足を報告してチェックポイントを返す。ドライバーがその担当を保留にした場合、自力で復帰しない。人間によるRetryRoleは既存権限での再試行であり、新しい権限の承認ではない。統括は保留担当の必要性を整理し、他の担当へ無許可の代行を依頼しない。

STOPは進行中のCLIと検証処理を中断し、DRAINは反復と統合ゲートを終えて停止するための要求である。停止や再起動を検知しても、自分でプロセスやOS自動起動を追加しない。再開時は保存された報告・編集・候補と実際の実行証拠を確認し、失われた途中経過を成功済みと推測しない。外部監査が未実行なら、preflightやローカル検証を外部監査の承認と記録しない。

長期運用では、新しい実装を増やす反復と、欠陥の修正、設計の整理、互換性確認、統合実演の反復を組み合わせる。毎回の小さな完了と、長期的な大きな目標を両立させる。
